# Releasing MacVPN and WinVPN

This is the maintainer's procedure for publishing a release, and the repository settings the in-app updaters rely on. From 2.0.0 every release is a joint release: one tag, one GitHub release with `MacVPN-X.Y.Z.dmg` for macOS and `WinVPN-X.Y.Z-x64.msi` and `WinVPN-X.Y.Z-arm64.msi` for Windows. From 2.1.0 the release also carries LinVPN's `linvpn_X.Y.Z_amd64.deb` and `linvpn_X.Y.Z_arm64.deb` (see [LinVPN](#linvpn)).

## How the updater finds releases

- The app asks `https://api.github.com/repositories/1422472799/releases/latest`. `1422472799` is the immutable numeric ID of `SepsiG/MacVPN`, stored as `MacVPNUpdateRepoID` in `app/src-tauri/Info.plist`, which the Tauri bundler merges into `MacVPN.app/Contents/Info.plist` (`scripts/build-dmg.sh` checks the result). A renamed, deleted and re-created, or transferred repository with the same name cannot serve updates (repo-jacking). Without a valid ID the app does not check for updates.
- `MacVPNUpdateRepo` (`SepsiG/MacVPN`) is used for the Help links and to check asset URLs: the DMG, its `.sha256` and its `.sig` are accepted only from `https://github.com/SepsiG/MacVPN/releases/download/<tag>/<file name>`.
- Both values are set statically in `app/src-tauri/Info.plist`. The release workflow does not rewrite them; it fails if they do not match `github.repository_id` and `github.repository`. If the repository is ever moved, update both keys in a normal commit.
- The release must contain `MacVPN-X.Y.Z.dmg`, `MacVPN-X.Y.Z.dmg.sha256` and `MacVPN-X.Y.Z.dmg.sig` and, for WinVPN, `WinVPN-X.Y.Z-x64.msi` and `WinVPN-X.Y.Z-arm64.msi`, each with its `.sha256` and `.sig` (nine files), and from 2.1.0 LinVPN's `linvpn_X.Y.Z_amd64.deb` and `linvpn_X.Y.Z_arm64.deb`, each with its `.sha256` and `.sig` (fifteen files in all); the tag must be `vX.Y.Z`. WinVPN asks the same releases endpoint and accepts an MSI only from the same download path. Users can opt in to a 24-hour delay, so a broken release can still be pulled before it reaches them.

## Offline signing (from 0.2.2)

Goal: even if the maintainer's GitHub account (or CI) is compromised, no update can be pushed to apps running 0.2.2 or later. Every update must carry an Ed25519 signature made with an offline key that only the maintainer holds.

- **Signed message** (exact bytes): `"macvpn-update-v1\n" + X.Y.Z + "\n" + sha256hex + "\n"`, where the version has no `v` and the SHA-256 of the DMG is lowercase hex. Pure Ed25519 (OpenSSL 3 `pkeyutl -sign -rawin`). WinVPN's MSIs (from 2.0.0) use their own domain, which also names the asset: `"winvpn-update-v1\n" + asset + "\n" + X.Y.Z + "\n" + sha256hex + "\n"`, the asset being exactly `WinVPN-X.Y.Z-x64.msi` or `WinVPN-X.Y.Z-arm64.msi` (`UpdateSignature::message_for`, `SignatureDomain`): a signature of one product or architecture never verifies for another. Same keys.
- **Asset:** `MacVPN-X.Y.Z.dmg.sig` (and `WinVPN-X.Y.Z-<arch>.msi.sig`), one line: the base64 of the 64-byte signature and a newline (max 1 KB).
- **In the app** (`crates/core/src/update.rs`, `UpdateSignature::PRIMARY_PUBLIC_KEY_BASE64` / `BACKUP_PUBLIC_KEY_BASE64`; the same keys as in 0.2.2–0.4.0): two raw 32-byte public keys, base64: primary `KfHXY5gQkjMA3e8bx8rIuPQ4x3zCuSJoMo3PYcMgbFk=` and backup `QUFfsn9koh06k4EX9lNPognIvQ84/Ox6lgZhShvVrmI=`. A signature by either is accepted. The updater verifies it against the SHA-256 it computes itself from the downloaded DMG or MSI (not just the `.sha256` file). A newer release without a `.sig` asset is not offered (**Check for Updates Now** says "Update waiting for signature"); a missing or invalid signature at install time stops the update with "The update is not signed by the MacVPN maintainer".
- **Older apps:** 0.2.1 and older do not check signatures. They install 0.2.2+ releases as before (the extra asset does not matter to them), but they are only protected by HTTPS and the SHA-256 from the same release.
- `scripts/sign-release.sh` reads the public keys from the Rust core source (`crates/core/src/update.rs`), so there is a single copy; `scripts/test-sign-release.sh` and the unit tests (`cargo test`, `sign_release_uses_the_embedded_keys`) check that both sides agree, and that the keys are still the ones the released 0.4.0 app embeds (`git show v0.4.0:…`).

### Key storage

- **Primary private key:** in the maintainer's login Keychain, as a generic password: service `MacVPN release signing`, account `primary`; the value is the base64 of the PEM. It was added with `-T /usr/bin/security`, so only `security` can read it without a prompt. `sign-release.sh` reads it through a process substitution (`-inkey <(security find-generic-password … -w | base64 -d)`): the PEM never touches the disk and is never printed.
- **Backup private key:** a PEM file kept offline in the password manager, **not** on the Mac. Use it only with `--backup-key <file>` (from a temporary location that you delete afterwards), e.g. if the Mac with the primary key is lost.
- Neither key is ever given to GitHub, CI or any other service. CI only creates a draft.

### If a key is lost or compromised

- **Primary lost** (Mac lost or wiped, Keychain item gone), not compromised: sign releases with `--backup-key` from the password manager. In the next release, generate a new primary key pair offline, put its public key in place of the old primary in `crates/core/src/update.rs`, and sign that release with the backup key (every app that has the old key set accepts it). From then on sign with the new primary.
- **Primary compromised** (someone else may have the private key): act at once. Generate a new primary key pair offline, replace the compromised public key in `crates/core/src/update.rs`, and publish a new release signed with the **backup** key. Until users install it, the attacker can sign updates for them, so also secure the GitHub account (a compromised key alone is not enough: the attacker also needs to publish a release on GitHub). Announce the incident.
- **Backup lost or compromised:** generate a new backup key pair, replace the backup public key in `crates/core/src/update.rs`, and sign that release with the primary key. If it was compromised, treat it like a compromised primary.
- **Both keys lost:** apps 0.2.2+ can no longer be updated in-app. Publish a release with new keys and tell users to install it manually from the DMG (after verifying it through another channel).
- Never generate keys in CI, and never commit a private key. Generate key pairs with OpenSSL 3: `openssl genpkey -algorithm ed25519 -out key.pem`, raw public key for the app: `openssl pkey -in key.pem -pubout -outform DER | tail -c 32 | base64`.

## Release procedure

The flow is: **tag → CI builds a draft → `scripts/sign-release.sh vX.Y.Z` on the maintainer's Mac → published.**

1. Merge everything for the release into `main`. CI (`.github/workflows/ci.yml`) must be green: the macOS jobs (`rust`, `node`, `dmg`) and the Windows jobs: `windows` and `windows-node`, which compile, lint and test the workspace for Windows; `msi`, which builds both WinVPN MSIs with `scripts/build-msi.sh` and keeps them as the workflow artifact `winvpn-msi`; and `windows-admin`, which installs OpenVPN Community and that MSI on the administrator runner and runs the admin test set (see [WinVPN](#winvpn)). **The release depends on this:** the release workflow does not run the tests again, it requires a successful CI run (every job) of the `push` of the tagged commit to `main`. So push to `main` first, wait for CI to pass, and only then tag that commit. The Rust jobs (`rust`, `dmg`, `windows`, `msi`, `windows-admin`) use a build cache of the compiled dependencies (`Swatinem/rust-cache`, one key per job and target set, written only by pushes to `main` and `develop`); it speeds up the checks only, and the release workflow never uses it.
2. If the root layer (`crates/helper`) changed, bump `crates/helper/VERSION` (1.1 shipped root layer 7; 1.2.0 to 1.5.0 ship **8** (the config goes to `mvpn` on stdin); 2.0.0 ships **9** (DNS manager, log caps, strongSwan credentials and concurrent connections); 2.0.3 ships **10** (`mvpn liveness`, dead-tunnel detection); 2.0.4 to 2.0.6 ship **11** (`mvpn traffic`, strongSwan's live traffic, and the strongSwan virtual IP in `mvpn status`); 2.0.7 ships **12** (the `up` frame's `x509=` / `private=` / `pkcs12=` lines: an IKEv2 client certificate imported in the app, staged into the run directory; the key password as a `private-…` / `pkcs12-…` secret bound to the key file)). The root layer is MacVPN's only: WinVPN's service is updated with the MSI. A new root version makes every user re-run **Authorize** with the admin password: say so in the release notes. Set the version (`X.Y.Z`) in `app/src-tauri/tauri.conf.json`, in `[workspace.package]` of `Cargo.toml` (then `cargo check` to update `Cargo.lock`) and in `app/ui/package.json` (`npm install --package-lock-only` updates the lock file). The three must agree (`scripts/build-dmg.sh` fails otherwise) and equal the tag (the workflow fails otherwise; it no longer rewrites the version). Before tagging, run the local-only checks:
   - the smoke test in both languages (`SMOKE_LANG=en scripts/smoke-manage.sh`, `SMOKE_LANG=hu scripts/smoke-manage.sh`, see `app/README.md`), and its Windows run in both languages (`scripts/win-smoke.sh en`, `scripts/win-smoke.sh hu`, in the test machine user's desktop session: sandbox and stand-ins only; it also covers WinVPN's native VPNs – the L2TP save and connect, the IKEv2 / SSTP connects, the Windows reasons, the Cisco IPsec copy, the Windows VPN client row and the account clean-up's confirmation – without dialling anything);
   - `scripts/check-windows.sh` (the part of the Windows compile check that runs on a Mac; the rest is the CI Windows job);
   - `scripts/bundle-baseline.sh dist/MacVPN.app` after `scripts/build-dmg.sh`: the built bundle compared with the previous release's baseline (`scripts/bundle-baseline/1.4.0/`; `BUNDLE_BASELINE_DIR` picks another one). Only the sizes of the two binaries may differ, unless the release says why;
   - `node scripts/l10n-baseline.mjs --check`: every macOS text is unchanged, unless the release changes a text on purpose;
   - the parts of `docs/manual-test-checklist.md` that the release touches (the full list runs after publishing, on the released DMG and MSI).
3. Tag the commit on `main` and push the tag:
   ```
   git checkout main && git pull
   git tag -s vX.Y.Z -m "MacVPN vX.Y.Z"   # or -a if you do not sign tags
   git push origin vX.Y.Z
   ```
4. `.github/workflows/release.yml` runs:
   - **ci-green** job (`actions: read` only, no checkout, runs no repository code): asks the GitHub API (`GET /repos/{owner}/{repo}/actions/workflows/ci.yml/runs?head_sha=<tagged commit>&branch=main&event=push`, with the workflow's `GITHUB_TOKEN`) for the newest CI run of the tagged commit pushed to `main`, waits for it if it is still running (at most 60 minutes; at most 5 minutes for a run that does not exist yet), and fails unless its conclusion is `success` and every job of its latest attempt (`/actions/runs/{id}/jobs?filter=latest`) succeeded. The log links the run. Both build jobs need it. If it failed because CI was not finished or had to be re-run, re-run the release workflow once CI is green; if CI failed, fix `main` and tag the new commit.
   - **build** job (`contents: read`, no persisted credentials): checks the tag format (`vX.Y.Z`), checks that the tagged commit is an ancestor of `origin/main`, checks the update source keys, checks that the version in `tauri.conf.json` equals the tag, builds the universal DMG with `scripts/build-dmg.sh` (UI build, `tauri build`, the release gate against debug-only code, the app and `mvpn` signed ad-hoc with the hardened runtime and no entitlements, Info.plist checks), checks the finished bundle again (repository ID, version, bundle ID, `codesign --verify --strict`), writes the `.sha256` (printed in the "SHA-256" step log), and uploads both as a workflow artifact. It runs no tests (CI did, see **ci-green**) and uses no build cache: the release artifacts are always built clean.
   - **build-windows** job (`contents: read`, `windows-latest`, no persisted credentials, no secrets): the same tag, `main` and version checks, then `scripts/build-msi.sh` (both MSIs, unsigned, with WiX's ICE validation and the release gates; no tests, no build cache, as in **build**); prints the `.sha256` files (the "SHA-256" step) and uploads artifact `msi`. It runs on every tag; see [WinVPN](#winvpn) for when its MSIs reach the draft.
   - **release** job (`contents: write`, and `id-token: write` + `attestations: write` for the provenance): downloads the artifact, re-checks the checksum, records **build provenance** for every file of the draft (the DMG, the MSIs and their `.sha256`) with GitHub's own `actions/attest-build-provenance` (pinned by full SHA): a Sigstore-signed SLSA attestation that this repository's `release.yml`, at this tag and commit, on a GitHub-hosted runner, produced exactly these bytes, stored in the repository's attestations (Actions → Attestations); then runs `gh release create --draft --repo "$GITHUB_REPOSITORY" --verify-tag`. Only this job gets the OIDC token: the build jobs, which run repository code, stay read-only. It does not check out or run repository code, and it never creates the `.sig`: CI must never hold the signing key. While `WINVPN_MSI_IN_RELEASE` is not `true` it needs only the **build** job (a failed **build-windows** does not hold back the MacVPN draft, which is exactly as before); when it is `true`, both build jobs must succeed and the two MSIs with their `.sha256` are added.
   The result is a **draft** release with the DMG and the `.sha256` and, while `WINVPN_MSI_IN_RELEASE` is `true` (as from 2.0.0), the two MSIs with theirs. Users do not see it yet. Its title is "MacVPN vX.Y.Z" and its description holds only the fixed installation and signing notes (Hungarian and English, with the WinVPN part when the MSIs are included); paste the release notes above them (see [Release notes](#release-notes)).
   Expected durations: CI on `main` takes about 25 minutes without a cache (the Windows jobs are the longest) and less once the `main` cache is warm. The release workflow takes about 12 minutes for the draft (ci-green under a minute when CI is done, then the clean DMG build, about 10 minutes; it used to take about 24 minutes with the tests); **build-windows** builds both MSIs clean, which takes longer, and holds back the draft only when `WINVPN_MSI_IN_RELEASE` is `true`.
5. On the maintainer's Mac (needs OpenSSL 3: `brew install openssl@3`; the GitHub CLI for the provenance check: `brew install gh`; `jq` and `curl` ship with macOS; a GitHub credential for `github.com` in the git credential helper, with write access to releases):
   **Before you sign**, compare the draft's DMG with a local build of the same tag, so that a tampered CI build is not signed:
   ```
   git checkout vX.Y.Z && scripts/build-dmg.sh          # local: dist/MacVPN.app
   # download MacVPN-X.Y.Z.dmg from the draft into a temporary directory, then:
   hdiutil attach -nobrowse -readonly -mountpoint /tmp/macvpn-draft MacVPN-X.Y.Z.dmg
   D=/tmp/macvpn-draft/MacVPN.app; L=dist/MacVPN.app
   codesign -dv "$D" 2>&1 | grep -E 'Identifier|flags'    # local.macvpn, flags=0x10002(adhoc,runtime)
   codesign -d --entitlements - --xml "$D" 2>/dev/null     # empty: no entitlements
   codesign --verify --strict --deep --verbose=2 "$D"
   diff <(plutil -convert xml1 -o - "$D/Contents/Info.plist") <(plutil -convert xml1 -o - "$L/Contents/Info.plist")
   for a in arm64 x86_64; do
     for app in "$D" "$L"; do lipo -thin $a "$app/Contents/Resources/root/mvpn" -output /tmp/mvpn-$a && shasum -a 256 /tmp/mvpn-$a; done
   done
   cmp "$D/Contents/Resources/root/VERSION" "$L/Contents/Resources/root/VERSION"
   hdiutil detach /tmp/macvpn-draft
   ```
   The Info.plist must be identical, both bundles signed with the hardened runtime (`runtime` in the flags) and no entitlements, and the root binary `mvpn` (the part that runs as root) must have the same SHA-256 per architecture. The builds are not bit-for-bit reproducible across machines when the toolchain or the build paths differ (they are embedded in the binaries), so build locally with the pinned toolchain (`rust-toolchain.toml`) and the Node version of the workflows (26.8.2); if a hash still differs, do not sign until the difference is explained.
   Then sign and publish:
   ```
   scripts/sign-release.sh vX.Y.Z
   ```
   It validates the tag, gets the token from `git credential fill` (never printed, only used in curl `Authorization` headers), finds the draft release for the tag (refuses a published one), downloads the DMG and `.sha256` (and both WinVPN MSIs with theirs, if the draft has them: both or neither) into a temporary directory, computes each SHA-256 locally and compares it with its `.sha256` asset, then **verifies each asset's build provenance**: `gh attestation verify <asset> --repo SepsiG/MacVPN --signer-workflow SepsiG/MacVPN/.github/workflows/release.yml --source-ref refs/tags/vX.Y.Z --source-digest <the tag's commit> --deny-self-hosted-runners` (the token goes to `gh` in `GH_TOKEN`, never on a command line). An asset without a valid attestation for exactly these bytes, this tag and the commit the tag names now (a moved tag is refused too) stops the script before anything is signed: a draft whose files were replaced after the build (a stolen write token) is never signed. It then **prints the hashes: compare them with the "SHA-256" steps of the workflow log** (a second, manual check). After you answer `y` to "Sign and publish vX.Y.Z (N assets)? [y/N]", it signs each asset with its product's message using the primary key from the Keychain (macOS may ask for the login Keychain password), verifies each signature against the embedded public keys, uploads `MacVPN-X.Y.Z.dmg.sig` (and the `.msi.sig` files), publishes the release (`draft=false`, `make_latest=true`) and prints its URL.
   - With the backup key: `scripts/sign-release.sh --backup-key /path/to/backup.pem vX.Y.Z`.
   - To fix the signature of an already published release: `--republish-sig` (deletes and re-uploads the `.sig`; the provenance is verified the same way, so releases made before the workflow recorded provenance – 1.x and older – cannot be re-signed with it). With immutable releases on, published assets cannot be changed; publish a new patch release instead.
   - If the provenance check fails: do not sign. Check the release run's "Build provenance" steps and the repository's attestations; a failure means the draft's bytes are not what this tag's release workflow built (or the tag moved). Delete the draft and re-run the release workflow (or tag a new patch version).
   - To test the setup without network: `scripts/sign-release.sh --dry-run --dmg some-file vX.Y.Z` signs the file with the Keychain key and verifies it against the embedded keys (add `--backup-key file` to test a key file); `--dry-run --msi some-file --arch x64|arm64 vX.Y.Z` does the same with WinVPN's message for that MSI. `scripts/test-sign-release.sh` runs the same with a throwaway key.
6. Check the release page: all assets are present (the DMG, both MSIs and, from 2.1.0, both `.deb`s, each with its `.sha256` and `.sig`: fifteen files), and the notes mention offline signing, the Gatekeeper and Keychain steps and the SmartScreen warning. Run **Check for Updates Now** in an older MacVPN (0.2.2 or later) and an older WinVPN. Then run `docs/manual-test-checklist.md` on the released DMG and x64 MSI.
7. If a release turns out to be broken or suspicious, delete it (or mark a newer fixed one as latest) quickly; users with the 24-hour delay will not have been offered it yet. A draft that should not be released can simply be deleted.

All actions are pinned to full commit SHAs with a `# vX.Y.Z` comment. Dependabot (`.github/dependabot.yml`) proposes updates weekly; review the upstream diff before merging such a PR.

## WinVPN

WinVPN is built from the same repository and tag as MacVPN (`scripts/build-msi.sh`, Git Bash on Windows): `WinVPN-X.Y.Z-x64.msi` and `WinVPN-X.Y.Z-arm64.msi`, each with its `.sha256`.

- **CI** (`ci.yml`, job `msi`) builds both MSIs on every push and pull request and keeps them as the workflow artifact `winvpn-msi` (7 days). They are never attached to a release from CI. Job `windows` runs `scripts/fetch-wireguard-nt.sh` and builds the helper's debug console (`mvpn.exe console`) before the tests: the service's tests load the pinned `wireguard.dll` and platform-win's client tests start the console. Its test run (every test binary of the Windows crates) includes WinVPN 2c's RAS tests: entries in private phonebooks under temp folders and the PSK store (winsys `ras`, platform-win `ras_engine`, `system_vpns`, `ras_sweep`, `admin_steps`) and the pure ones (`ras_pure`, `ras_connect`, `ras_editor`, `system_vpns_pure`, core `ras_plan`, helper `ras_logoff`). Nothing dials: the RAS dial tests need an interactive logon session and the CA trust test a UAC prompt, so they are ignored everywhere (`scripts/ignored-everywhere.txt`: winsys `ras` 3, `ras_engine` 5, `system_vpns` 1, `admin_steps` 1) and run by the maintainer from the checklist (`docs/manual-test-checklist.md`, the WinVPN native VPN section, "Takarítás és egyéb"). Job `rust` also runs `scripts/test-win-smoke.sh` (print mode) and `scripts/test-vpn-lab.sh` (the VPN test lab's profiles, PKI and dry runs, with the image's OpenSSL 3; the `docker compose` checks skip themselves on a runner without Docker).
- **The administrator job** (`ci.yml`, job `windows-admin`, after `msi`): GitHub's Windows runners run as an administrator, so this job does what the standard-user tests and the Windows test machine's SSH account cannot. `scripts/ci-install-openvpn.sh` downloads the pinned OpenVPN Community x64 MSI (`scripts/pins/openvpn.txt`), refuses any SHA-256 but the pin and any Authenticode signer but the pinned one, installs it with the pinned `ADDLOCAL` features (`openvpn.exe`, DCO, TAP-Windows6; it refuses to run unless `CI` is set, and leaves OpenVPN's Interactive Service as the MSI set it: that install is not WinVPN's), and checks the `ovpn-dco` and `tap0901` driver services and their `.sys` versions. Then the x64 MSI of job `msi` is installed with `msiexec.exe /qn` (its `.sha256` checked first) and the `WinVPN` service must be running. The admin test set (tests ignored everywhere else, `scripts/ignored-everywhere.txt`) runs: `service_admin` (the installed service answers, the data directory's ACL, the recovery settings), `wireguard_admin` (a WireGuard adapter up and down), `openvpn_installed` (the installed OpenVPN passes the service's trust checks), `openvpn_e2e` (OpenVPN end to end through the installed service to a local `openvpn.exe` server on loopback with a throwaway PKI from Git's `openssl.exe`: one DCO connection, one TAP-Windows6 connection) winsys `service_pipe` (the installed service's pipe is owned by SYSTEM) and winsys `cert_store_admin` (a CA enters the computer's Trusted Root store with the TLS-only usage property, as **Trust This CA in Windows…** adds it, and is removed). On failure it prints the two install logs, `C:\ProgramData\WinVPN\service.log` and the connection logs (masked). The same set is in the "WinVPN: a szolgáltatás, OpenVPN, WireGuard, frissítés" section of `docs/manual-test-checklist.md` ("Az admin teszthalmaz"), for the maintainer when the job was not green (elevated Git Bash). **Before a release with MSIs** (`WINVPN_MSI_IN_RELEASE` = `true`), `windows-admin` must have been green on the temporary branch with the release's content, as well as on the `main` push (**ci-green** requires every job).
- **Release** (`release.yml`, job `build-windows`) builds them clean (no cache, no tests: **ci-green** requires the green CI run) on every tag. They are attached to the draft only when the repository variable **`WINVPN_MSI_IN_RELEASE`** (Settings → Secrets and variables → Actions → Variables) is exactly `true`. It was unset for 1.x (those drafts carry only the DMG) and is `true` from 2.0.0 on; leave it so. With `false` or unset, a failed **build-windows** would not hold back a MacVPN-only draft (an emergency MacVPN fix while the Windows build is broken), and WinVPN users would not be offered that release. When it is `true`, the release notes also say that the MSIs are not Authenticode-signed (SmartScreen warns once: More info → Run anyway), that an administrator installs them, that updates are protected by the same offline Ed25519 signatures, and that WinVPN installs the WinVPN Service (OpenVPN and WireGuard connections) and WireGuard's signed `wireguard.dll`, with OpenVPN Community installed from System Status when needed.
- **Signing:** `scripts/sign-release.sh vX.Y.Z` signs every MSI it finds in the draft with WinVPN's own domain, which names the asset: `"winvpn-update-v1\n" + asset + "\n" + X.Y.Z + "\n" + sha256hex + "\n"`, and uploads `WinVPN-X.Y.Z-x64.msi.sig` and `WinVPN-X.Y.Z-arm64.msi.sig` next to `MacVPN-X.Y.Z.dmg.sig` (same keys). Both MSIs or neither: a draft with only one of them is refused. Each MSI's build provenance is verified like the DMG's before anything is signed. Compare the printed hashes with the "SHA-256" steps of both build jobs.
- **Authenticode is off.** `scripts/build-msi.sh` signs with signtool only when `WINVPN_SIGN_THUMBPRINT` (40 hex digits, a certificate in the build machine's store) and `WINVPN_SIGN_TIMESTAMP_URL` (an RFC 3161 server) are set. Neither is set in CI or in the release workflow (`build-windows` refuses a thumbprint), and no secret is needed for the unsigned build.
- **Engine updates need no WinVPN release** (the maintainer's decision, 2026-10-24; 2b plan, decisions 4 and 6 as amended, "As built (fix4)"): the WinVPN Service updates wireguard-nt itself from https://download.wireguard.com/wireguard-nt/ (System Status → WireGuard → "Update"; the DLL's Authenticode signer `WireGuard LLC` is checked before it is kept and at every load, and it is applied only while no WireGuard connection is up), and System Status offers the newest OpenVPN Community (winget's, or the newest official MSI from https://openvpn.net/community-downloads/, checked by its Authenticode signer `OpenVPN Inc.`). **The pins below are minimums and the offline/bootstrap fallback only:** the bundled `wireguard.dll` and the pinned OpenVPN MSI are what WinVPN uses when nothing newer can be found (no network, the page changed). Raising them at a release is optional: do it when an engine release matters for a fresh offline install (a security fix), not for every engine release.
- **The bundled wireguard-nt** (`scripts/pins/wireguard-nt.txt`, 1.1; the minimum and the fallback): `scripts/fetch-wireguard-nt.sh` downloads the zip from `download.wireguard.com`, checks its SHA-256 and each DLL's (amd64, arm64) and, on Windows, the DLLs' Authenticode signer (`WireGuard LLC`); `build-msi.sh` runs it and gates the DLL again, and the release workflow's **build-windows** runs it as its own step. The service compiles the DLL's SHA-256 in and refuses any other `wireguard.dll` next to its exe; a newer `wireguard.dll` the service downloaded itself (`C:\ProgramData\WinVPN\engines\wireguard-nt\`) needs no pin, only the signer and a version above the bundled one. **To change the pin:** download the new `wireguard-nt-<v>.zip` from https://download.wireguard.com/wireguard-nt/ at least twice, compare its SHA-256 with the one the official WireGuard for Windows build pins (`build.bat` of wireguard-windows), record the zip's and both DLLs' SHA-256 and the signer in the pin file (with the source in its comments), check `include/wireguard.h` against the struct layout in `crates/helper/src/windows/wg_nt.rs` (`scripts/wg-nt-layout.c` with MSVC), replace `scripts/notices/wireguard-nt-LICENSE.txt` if the zip's `LICENSE.txt` changed and regenerate `THIRD-PARTY-NOTICES.windows.txt`; then `scripts/fetch-wireguard-nt.sh` on Windows, the helper's tests and `wireguard_admin` (CI `windows-admin`).
- **The pinned OpenVPN Community** (`scripts/pins/openvpn.txt`, 2.7.8-I001): where winget exists, System Status installs OpenVPN through winget, which takes winget's newest version (not the pin); the pinned MSI is the fallback without winget (or when winget did not install both drivers). "Update" offers the newest of winget's offer and the newest official MSI (the newest one OpenVPN's download page links, found at runtime; the pin when the page cannot be read or links nothing newer) (CI's `windows-admin` job installs the pin with `scripts/ci-install-openvpn.sh`). The pin is the minimum and the offline fallback (fix4): raising it at a release is optional; the service accepts any `OpenVPN Inc.`-signed version from `min_version` on. **To change the pin:** take the new `OpenVPN-<v>-I<nnn>-{amd64,arm64}.msi` from https://openvpn.net/community-downloads/ (`swupdate.openvpn.org`), verify both `.asc` with GnuPG against the OpenVPN security mailing list key, check `Get-AuthenticodeSignature` on both MSIs and on the `openvpn.exe` inside them (Valid, signer `OpenVPN Inc.`), read the Feature table of both MSIs (`scripts/msi-query.ps1`: the features for `openvpn.exe`, DCO and TAP-Windows6 and nothing else; a feature unknown to the MSI fails the install) and the driver versions; write the URLs, SHA-256s, features, version and signer into the pin file (with the evidence in its comments), regenerate the app's copy with `WINVPN_WRITE_PINS=1 cargo test -p macvpn-helper --test ovpn_windows` (`crates/platform-win/src/pure/openvpn_pins.rs`), update the driver versions (`DRIVERS`) in `scripts/ci-install-openvpn.sh`, re-check `ovpn_args::choose_driver` and `ovpn_log::dco_incompatible` against the new version's `options.c`, `dco.c`, `comp.c`, `init.c` and `ssl.c`, and let `windows-admin` run (the install script, `openvpn_installed`, `openvpn_e2e`).
- **Signer pins** (M-1 of the 2.0.0 security review): besides the signer's name, both pin files list `signer_ca_spki_sha256`, the SHA-256 of the DER `SubjectPublicKeyInfo` of each CA that may have issued the publisher's code-signing certificate (comma-separated). The service loads a `wireguard.dll` (bundled or downloaded) and runs `openvpn.exe`, and the app installs an OpenVPN MSI (pinned or the newest official one), only when the Authenticode chain Windows built has one of those keys above the signer: a certificate named `WireGuard LLC` or `OpenVPN Inc.` from any other root (an operator CA or a TLS-inspection root on the PC) is refused. Pinned today: wireguard-nt `Sectigo Public Code Signing CA EV R36` (`4c2655…c112`), OpenVPN `DigiCert Trusted G4 Code Signing RSA4096 SHA384 2021 CA1` (`4448d3…ab32`). A yearly leaf renewal under the same CA needs nothing. **When a publisher changes CA**, a newer engine is refused: a downloaded wireguard-nt is not loaded (`service.log`: "downloaded wireguard.dll … refused: it is signed by "WireGuard LLC" but not under a pinned CA (its chain's key SHA-256: …)"; the bundled DLL stays in use), a newer OpenVPN MSI is not installed and a newer `openvpn.exe` is reported as "signed by OpenVPN Inc., but not through a certificate authority WinVPN knows". **To add the new CA's key:** take a file signed under it from the official source (the new wireguard-nt zip, verified as above; the new OpenVPN MSIs, verified with GnuPG as below), extract its signature's certificates (a PE file: the certificate table's PKCS #7, e.g. `osslsigncode extract-signature`; an MSI: its `\x05DigitalSignature` stream, e.g. `gsf cat <msi> $'\x05DigitalSignature'`), list them with `openssl pkcs7 -inform der -print_certs`, and for the certificate that issued the leaf compute `openssl x509 -pubkey -noout | openssl pkey -pubin -outform der | openssl dgst -sha256`; check that this CA belongs to a public code-signing hierarchy (its issuer, its validity) and that the leaf's subject is the publisher. **Append** the key to `signer_ca_spki_sha256` (keep the old one while released versions are still signed under it), record the chain in the pin file's comments, regenerate `openvpn_pins.rs` (`WINVPN_WRITE_PINS=1`, below), update the expected values in `crates/helper/tests/{wg_windows,ovpn_windows}.rs` and run `cargo test -p macvpn-winsys --test trust` and the helper's `wgdll` tests on Windows (they read the real pinned DLL's chain).
- **ICE validation** always runs in CI and in the release workflow. `WINVPN_WIX_NO_ICE=1` (linking without validation, for a machine whose Windows Installer service is unreachable, such as an SSH session) is refused whenever `CI` is set, which GitHub Actions always sets.

## LinVPN

LinVPN (Linux) is built from the same repository and tag (`scripts/build-deb.sh`, on Linux, one architecture per run): `linvpn_X.Y.Z_amd64.deb` and `linvpn_X.Y.Z_arm64.deb`, each with its `.sha256`. Its first release is **2.1.0**, joint with MacVPN and WinVPN; the L-a preview builds (version 2.0.5) are never released.

- **Release** (`release.yml`, job `build-linux`) builds both `.deb`s clean on every tag, natively on GitHub's `ubuntu-24.04` (amd64) and `ubuntu-24.04-arm` (arm64) runners, with every gate of `build-deb.sh` (the package name `linvpn`, the version and architecture, exactly the two maintainer scripts `postinst` and `prerm` that turn `linvpn-logd.socket` on and off, checked byte for byte, no debug code, SQLCipher on the vendored OpenSSL linked statically, the pinned file list). They are attached to the draft, with their `.sha256` and build provenance, only when the repository variable **`LINVPN_DEB_IN_RELEASE`** (Settings → Secrets and variables → Actions → Variables) is exactly `true`. It was unset until 2.0.7; **set it to `true` before 2.1.0's tag** and leave it so, as `WINVPN_MSI_IN_RELEASE` from 2.0.0. With it unset, a failed **build-linux** does not hold back the MacVPN and WinVPN draft (an emergency fix while the Linux build is broken), LinVPN users are offered nothing, and the **release** job's log and annotations warn that the draft has no `.deb` (delete such a draft, set the variable and re-run the workflow).
- **Signing:** `scripts/sign-release.sh vX.Y.Z` signs every `.deb` it finds in the draft with LinVPN's own domain, which names the asset: `"linvpn-update-v1\n" + asset + "\n" + X.Y.Z + "\n" + sha256hex + "\n"`, and uploads `linvpn_X.Y.Z_amd64.deb.sig` and `linvpn_X.Y.Z_arm64.deb.sig` (same keys as MacVPN and WinVPN). Both `.deb`s or neither: a draft with only one of them is refused. Each `.deb`'s build provenance is verified like the DMG's before anything is signed; compare the printed hashes with the "SHA-256" steps of **build-linux**.
- **Dry run:** `scripts/sign-release.sh --dry-run --deb FILE --arch amd64|arm64 vX.Y.Z` signs a file with LinVPN's message for that asset name and verifies it against the embedded keys (`scripts/test-sign-release.sh` covers it with a throwaway key).
- **The installed LinVPN** checks the same releases endpoint (the repository ID is compiled in, as in WinVPN), accepts a `.deb` only from the same download path and only with a valid `.sig`, and installs it through pkexec and its root step, which verifies the signature, the package name, the architecture and the version again (no downgrade). A release without the `.deb`s offers LinVPN users nothing.
- **LinVPN's NetworkManager OpenVPN service** (`packaging/linux/nm-linvpn-openvpn/`, see [architecture.md](architecture.md#linvpns-networkmanager-openvpn-service)) is built into every `.deb` from the upstream tarball `NetworkManager-openvpn-1.12.5.tar.xz` (`download.gnome.org`), checked against the SHA-256 pinned in `scripts/pins/nm-openvpn.sha256`, plus `linvpn-nm-openvpn.patch`; the `.deb` carries the tarball, the patch and its README in `/usr/share/linvpn/source/` (GPL-2.0-or-later; keep them in step with the binaries). Before each release:
  - **Upstream security fixes:** check [NetworkManager-openvpn's releases](https://gitlab.gnome.org/GNOME/NetworkManager-openvpn/-/tags) and the Ubuntu and Debian security trackers for `network-manager-openvpn`. A fix in the service or its helper means moving the pin: put the new version and its SHA-256 (the same as GNOME's published `.sha256sum`) into `scripts/pins/nm-openvpn.sha256` and `scripts/build-nm-linvpn-openvpn.sh`, rebase the patch, run `scripts/test-build-nm-linvpn-openvpn.sh` and `scripts/test-build-deb.sh` on the Linux VM, and check that NetworkManager-openvpn's `valid_properties[]` still match what `nm_plan::openvpn` writes (`crates/core/tests/nm_plan_openvpn.rs`). A fix only in OpenVPN itself needs nothing from LinVPN: the system's `openvpn` package is used.
  - **Offering the patch upstream:** the helper part (`--redirect-info`, reading OpenVPN 2.7's `route_redirect_gateway_ipv4/6`) is what those variables were added for. Offer it to NetworkManager-openvpn (a merge request on GNOME's GitLab, without LinVPN's `linvpn-*` keys and syslog ident); note its state here. Once a distribution LinVPN supports ships it, LinVPN can return to the stock plugin.
- **The release notes** for a release with the `.deb`s say that LinVPN installs with `sudo apt install ./linvpn_X.Y.Z_<arch>.deb` on Ubuntu 24.04+ or Debian 13, that updates are protected by the same offline Ed25519 signatures and installed after an administrator's password, that VPNs connect through NetworkManager (with the plugins System Status installs), and what LinVPN does not do yet.

## Team catalog formats (from 1.3.0)

Team catalogs add file formats that other MacVPN installations read, so a release that changes one of them must say so in the release notes and keep the older readers in mind. The formats are versioned independently of the app version:

| What | Where | Version in 1.3.0 | Rule |
|---|---|---|---|
| Catalog file `<name>.macvpncatalog` | `crates/core/src/catalog/format.rs` | magic `MVPNCAT1`, header `format` 1 | A higher `format` is refused by older apps ("made by a newer MacVPN"). The signature domain is `macvpn-catalog-v1\n`, distinct from the update domain `macvpn-update-v1\n`, so the two signatures can never be swapped. Max 8 MB. |
| Catalog payload (inside the encrypted part) | `crates/core/src/catalog/payload.rs` | `version` 1 | Unknown keys are refused, so a new field needs a new payload version, and subscribers on the old version stop applying until they update. |
| Subscription string `macvpn-sub:` | `crates/core/src/catalog/subscription.rs` | `v` 1 | A higher `v` is refused. |
| Admin key file `.macvpnadminkey` | `crates/core/src/catalog/admin_file.rs` | magic `MVPNAKEY`, format 1 | Password-sealed like a backup. |
| Vault schema | `crates/core/src/vault/schema.rs` | 2 | Migrations are append-only; the first 1.3 launch copies the old database to `vault.db.bak-v1`. 1.2 opens a v2 vault read-only. |
| Full backup payload | `crates/core/src/vault/backup.rs` | 2 | v1 backups are migrated on restore; a 1.2 app refuses a v2 backup ("made by a newer MacVPN"). |

Release checks for 1.3.0 and later:
- The root layer does not change for team catalogs (`crates/helper/VERSION` stays 8). The `scripts/build-dmg.sh` release gate fails if the `mvpn` binary contains `MVPNCAT1` or `macvpn-catalog-v1` (catalog code must never reach the root binary).
- Document types (from 1.4.0): `.ovpn` and `.sstp` (both Default) open in MacVPN through imported UTIs (`local.macvpn.ovpn`, `local.macvpn.sstp`) that conform to `public.data` and `public.item`, never to a text type (plain text is a "safe" download type Safari may open by itself; a downloaded, quarantined file is imported only after a confirmation), `.macvpncatalog` (Owner) through its exported UTI `local.macvpn.catalog` and opens **Add team catalog…** with the file preselected (the fingerprint step stays mandatory), and `.conf` is listed only under "Open With" (Alternate, by the extension, no type declared). `.macvpnadminkey`, `.macvpnbackup` and `.mobileconfig` are never claimed. `scripts/build-dmg.sh` checks these keys in the built `Info.plist`. The 1.0–1.3 updaters' `verify_bundle` reads only the bundle ID and the version from `Info.plist`, so the new keys do not affect an update.
- The 1.3.0 release notes say: every team member needs 1.3.0 to subscribe or publish; the vault moves to schema v2 on the first launch (a backup copy is made; 1.2 can still read the vault, read-only, but cannot edit it or restore a backup into it, so there is no way back to editing in 1.2); MacVPN never uploads a catalog; HTTPS catalogs are fetched without a proxy.
- A release that changes a catalog format runs the "Csapatkatalógusok (1.3)" section of `docs/manual-test-checklist.md` (two Macs, a file share and an HTTPS host) and its WinVPN part ("Csapatkatalógus fájlforrással", "Csapatkatalógus HTTPS-en").

## Licences and third-party notices

Every release must ship the licence texts of what it bundles:

- `LICENSE` at the repository root: MacVPN's own MIT licence.
- `THIRD-PARTY-NOTICES.txt` in the repository and inside the app bundle (copied by `scripts/build-dmg.sh`; the build fails without it, and when it is not what the generator writes now). It covers:
  - **SQLCipher** (from 1.2.0, statically linked into the app for the vault): its BSD-style licence in full, with the copyright notice of **Zetetic LLC**. Clause 2 of that licence requires binary redistributions to reproduce the copyright notice, the list of conditions and the disclaimer in the documentation or other materials provided with the distribution; `THIRD-PARTY-NOTICES.txt` in the bundle is how MacVPN meets it. SQLite itself is public domain (no notice required, but list it).
  - Every Rust crate linked into the app or `mvpn` and every JS package bundled into the web view, with its licence expression and the licence files it ships. The list is generated, not written by hand: `node scripts/third-party-notices.mjs` (after `cargo fetch --locked` and `npm ci` in `app/ui`) rewrites the file from `cargo metadata` and `node_modules`; `--check` only compares. Regenerate it whenever a dependency changes and review the diff.
- The release notes mention the licence files only when they change.
- From 1.5.0 `Cargo.lock` also holds crates that only a Windows build links (`openssl-src`, `openssl-sys`, for SQLCipher on Windows). The generator leaves them out of `THIRD-PARTY-NOTICES.txt`, which lists what the macOS release bundles. The MSIs ship `THIRD-PARTY-NOTICES.windows.txt` (installed as `C:\Program Files\WinVPN\THIRD-PARTY-NOTICES.txt`), which also carries the wireguard-nt licence (`scripts/notices/wireguard-nt-LICENSE.txt`).

## Repository settings (not code)

These protect the release channel and must be set in the GitHub UI by the account owner:

- **Two-factor authentication with a hardware security key** (passkey / FIDO2) on the owner account; remove SMS as a fallback. Whoever controls this account can publish an update to users of 0.2.1 and older (0.2.2 and later also require the offline signature, see above).
- **Immutable releases** (Settings → General → Releases): published release assets and their tags cannot be changed or replaced afterwards.
- **Tag protection ruleset** (Settings → Rules → Rulesets) for `refs/tags/v*`: restrict creation, update and deletion to the maintainer, and block force pushes. Optionally require signed tags.
- **Branch protection / ruleset for `main`**: no force pushes or deletion, require the CI check, since the release job only accepts tags on `main`.
- **Actions settings**: default `GITHUB_TOKEN` permissions set to read-only; allow only GitHub-owned actions plus the one third-party action, `Swatinem/rust-cache@*` (CI's build cache; the release workflow does not use it). If the setting allows only GitHub-owned actions, the five Rust CI jobs (`rust`, `dmg`, `windows`, `msi`, `windows-admin`) fail at that step.
