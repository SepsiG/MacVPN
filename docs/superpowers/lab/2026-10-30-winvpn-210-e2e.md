# WinVPN 2.1.0 end-to-end lab notes

## Setup

The VPN lab (`scripts/vpn-lab/`) ran in Docker on the Linux test VM, published on that VM's LAN address; its UDP
500/4500 were DNAT'd to the lab's ipsec container (so the lab server is behind NAT as Windows sees it). The lab's
services network is reachable from the Windows test VM only through a tunnel. The client profiles were the lab's
`client/windows` folder (copied to the Windows VM's user profile, never into the repository); the credentials came
from its `l2tp.txt` / `cisco-ipsec.txt` sheets, read by the test process only.

System: Windows 11 x64 (Hungarian display language), the released WinVPN 2.1.0 MSI with the WinVPN Service running,
OpenVPN Community 2.7.7 (DCO 2.8.13, TAP-Windows6 9.27), the service's wireguard-nt. Everything ran as the standard
user; nothing was installed, elevated, or restarted.

The tests are `crates/platform-win/tests/lab_e2e.rs` (develop 2ed3e57 + branch `win-lab`). They use the app's own
`HelperClient` on Windows (`RasHelper`): OpenVPN and WireGuard through the **installed** service's pipe
(`\\.\pipe\WinVPN`, trusted only as SYSTEM-owned), IKEv2 / SSTP / L2TP through the real RAS with a `RasEngine` over a
temp data folder (its own private phonebook, cleared and deleted after each case; WinVPN's own phonebook was never
touched). The service refuses network logons and RAS needs an interactive logon, so the tests ran in the standard
user's desktop session through a one-shot scheduled task (`/IT`, a headless console), one at a time. Each case checks
that no lab secret is in the connection's log as the app reads it (the service's masked log, or the RAS log).

## Maintainer checkpoints (need administrator rights)

1. **Trust the lab CA in Windows** (SSTP `cert=ca`, IKEv2): in WinVPN, open an SSTP connection made from
   `sstp-ca.sstp` (or the IKEv2 EAP one) → **Trust This CA in Windows…** → confirm the UAC prompt. (Or, as an
   administrator: `certutil.exe -addstore Root lab-ca.cer`.) The CA is the lab's throwaway "MacVPN Lab CA".
2. **Allow L2TP Behind NAT** (L2TP/IPsec to the lab, which is behind DNAT): WinVPN's **Allow L2TP Behind NAT…**
   after an L2TP failure (UAC), then **restart Windows** (the IPsec policy agent reads the value at start).

Then the remaining cases (as the standard user, in the desktop session): `lab_win_l2tp`, `lab_win_ikev2_eap`,
`lab_win_sstp`, plus an IKEv2 EAP with a wrong password (open item 1).

## Open items

1. **IKEv2 13801 with EAP is always "Authentication failed (EAP)"** (design question, not changed): with the lab CA
   not trusted, the dial fails with 13801 before any EAP round, and WinVPN says the sign-in failed (a sign-in failure:
   the app asks for the password again) instead of pointing to the CA. Windows uses 13801 both for an untrusted /
   unsuitable server certificate and for refused credentials. Whether a wrong EAP password gives 13801 or 691 once
   the CA is trusted decides the fix (e.g. 13801 with EAP naming both causes, and **Trust This CA in Windows…** when
   the connection has a custom CA). To be measured after checkpoint 1.
2. OpenVPN's status has no interface name (`iface` empty) on Windows; the traffic comes from the service's
   `>BYTECOUNT`, so nothing depends on it.
