Steps use checkbox (`- [ ]`) syntax for tracking. The spec is `docs/superpowers/specs/2026-10-20-cross-platform-winvpn-design.md` (sections 2, 4.2, 4.3, 5, 6, 8, 9). Every earlier spec (vault, control API, team catalog) and every rule, decision and "As built" note of the 2a plan (`docs/superpowers/plans/2026-10-21-winvpn-2a-foundations.md`) and the 2b plan (`docs/superpowers/plans/2026-10-22-winvpn-2b-service-openvpn-wireguard.md`, including its amended decisions 4 and 6 of 2026-10-24) still applies. Where this plan and the spec disagree, the spec wins, except where "Resolved points" below says why the plan deviates. Follow the existing patterns of the crate you work in (read a neighbouring module first). The 2b plan is the reference for rigor and style.

**Goal:** WinVPN connects the four native kinds MacVPN has, from a standard user account, without the WinVPN Service and without an administrator for the normal case: **L2TP/IPsec** (PSK, the MacVPN form), **IKEv2** (MacVPN's strongSwan `swanctl.conf` connections, translated to the Windows IKEv2 client where the settings are supported; precise "not supported on Windows" reasons otherwise), **SSTP** (MacVPN's `.sstp` form) — all through RAS phonebook entries in a **WinVPN-private phonebook**, dialled with `RasDialW` in the user's own process, credentials passed at dial time from the vault; the user's own Windows VPNs are listed as **system VPNs** (live list, stored secrets, connect/disconnect) like `scutil --nc list` on macOS; **Cisco IPsec** (IKEv1 + XAUTH), which Windows has no client for, gets the outcome the maintainer chooses in open question 1 (default implemented here: a clear "not supported on Windows" state with a one-click L2TP/IPsec copy). A parity audit (Task 1) lists every MacVPN feature and its Windows state, so that every gap left after 2b gets a task here or is named as covered by the features plan. MacVPN behaviour stays exactly as it is.

**Architecture:** the native VPNs are driven **in the app process** (the user's own context), as the spec 4.2 says ("They start through `RasDial` and stop through `RasHangUp` in the user context"). All new Win32 calls (RAS: `rasapi32.dll`, `rasdlg.dll`; the phonebook INI keys; the change notifications) go into one new module of `macvpn-winsys`, `winsys::ras`, behind a safe API with no `unsafe` outside winsys. The pure parts — the translation of a connection into a phonebook entry description (`macvpn_core::ras`: L2TP, SSTP, IKEv2-from-`swanctl.conf`, the IPsec policy, the entry name) and the dial state machine, the log lines and the error texts (`macvpn_platform_win::pure::ras_*`) — compile and are tested on every OS. `platform-win`'s `RasEngine` implements `NativeController` + `NativeProfiles` (L2TP, Cisco, the system VPNs) and serves the helper kinds IKEv2 (`strongswan`) and SSTP behind the existing `HelperClient` (the service client routes those two kinds to it), so the manager, the editors, the Log tab, the credential prompt and the control API work unchanged. The WinVPN Service gets one small addition: at a user's logoff it also hangs up that user's WinVPN RAS connections (2b decision 2). Administrator-only steps (a CA for the computer's trusted roots, L2TP behind NAT) are offered through a UAC prompt from the app, never through the service.

**Tech Stack:** Rust 1.99.1 (pinned), edition 2024, Tauri 2.12 (WiX 3 MSI), `windows-sys =0.61.2` (already in `Cargo.lock`; only new *features*: `Win32_NetworkManagement_Rras`, `Win32_System_WindowsProgramming` for the INI calls if needed), Svelte + TS, bash (Git Bash on Windows), Node 26.8.2. No new crate.

## Open questions for the maintainer (only these block something)

1. **Cisco IPsec on Windows (blocks Task 12's final shape and the parity claim).** Windows has no IKEv1-XAUTH client, and no maintained, redistributable, signed engine exists (evidence in "Cisco IPsec on Windows" below). Choose:
   - **A (implemented by this plan as the default):** a Cisco IPsec connection on Windows stays editable, exportable, backed up and shared through catalogs, but cannot connect; the card says **"Cisco IPsec is not supported by Windows. Ask your VPN administrator for L2TP/IPsec or IKEv2 access, or make an L2TP/IPsec copy of this connection."**, and the editor has **Make an L2TP/IPsec Copy** (same server, account, password and PSK). Parity is then *not* complete for this one kind: the user guide and the release notes say so.
   - **B:** a WinVPN-built IKEv1 engine (IKEv1 Main/Aggressive Mode with PSK + XAUTH + Mode Config, ESP in user space over a Wintun adapter driven by the WinVPN Service). Real parity, but a new security-critical protocol implementation (months of work and its own review); it would get its own spec and plan after 2.0.0 or delay 2.0.0.

## Resolved points (the design decisions, with reasons)

### How WinVPN creates and drives native VPNs: the RAS API, in the app, in a private phonebook

- **RasApi32, not PowerShell, not the service.** WinVPN writes entries with `RasSetEntryPropertiesW`, reads them with `RasGetEntryPropertiesW`, dials with `RasDialW`, hangs up with `RasHangUpW`, and watches with `RasConnectionNotificationW` / `RasGetConnectStatusW` / `RasEnumConnectionsW` (Microsoft Learn, *Remote Access Service (RAS) – ras.h*; `RASENTRYW` documents `dwVpnStrategy` = `VS_L2tpOnly` / `VS_SstpOnly` / `VS_Ikev2Only`, the `RASEO_*` / `RASEO2_*` option bits and the Windows 8 additions used here).
  - *PowerShell `Add-VpnConnection` (VpnClient module, CIM class `MSFT_VpnConnection`)* is rejected: its `-L2tpPsk` takes the PSK as a plain command-line string (a secret in argv, visible to every process of the user and to process-creation auditing); it starts a PowerShell host (about a second, and the "no shell" rule); it works only on the two default phonebooks; and driving the CIM provider over COM/WMI from Rust would be a large new `unsafe` surface for the same RAS calls underneath. PowerShell is used **only by the spike** (Task 2) to capture Microsoft's own reference entries for the tests.
  - *The WinVPN Service* is rejected for native VPNs: a RAS connection dialled by the user's own process belongs to the user's logon (Windows ends it at logoff by default; Microsoft Learn, *RAS connections are disconnected when you log off* / `KeepRasConnections`), needs no privilege for a per-user phonebook, and keeps the service's attack surface where 2b left it (spec 4.2: "no service needed"). The service only gains a logoff safety net (Task 10).
- **A WinVPN-private phonebook per user**: `%LOCALAPPDATA%\WinVPN\ras\WinVPN.pbk` (the data directory's private ACL: the user and SYSTEM; RasMan runs as SYSTEM and reads it), passed as `lpszPhonebook` to every call. Reasons:
  - **No collision with the user's own entries, ever**: the user's entries live in `%APPDATA%\Microsoft\Network\Connections\Pbk\rasphone.pbk` and the all-users phonebook `%ProgramData%\Microsoft\Network\Connections\Pbk\rasphone.pbk`; WinVPN never writes either.
  - **No administrator**: the all-users phonebook needs administrator rights to write (`RasSetEntryPropertiesW` fails with `ERROR_ACCESS_DENIED` for a standard user; Microsoft Learn, *RasSetEntryProperties*, "phone-book file" and the All Users profile notes); a per-user phonebook does not.
  - **The managed entries are WinVPN's**: they do not appear in Settings → Network & internet → VPN (which shows the default phonebooks), so the user cannot half-edit them there and the macOS rule "MacVPN's copies live in the vault" holds. Connecting and disconnecting is done in WinVPN (popover, Connections window, control API). This is a deliberate difference from macOS, where an approved profile also appears in System Settings: on Windows the entry is an implementation detail (the user guide says so).
  - **Clean removal**: deleting a connection deletes its entry (Task 6/8); the file goes with `%LOCALAPPDATA%\WinVPN`.
  - **Fallback if the spike fails** (Task 2 decides; recorded there; **Task 2: not needed** — the private phonebook writes, reads and dials for L2TP, SSTP and IKEv2): if `RasDialW` with a phonebook outside the two default locations does not work on Windows 11 for one of the three strategies, WinVPN uses the user's default phonebook for that strategy with the same entry names, and refuses to overwrite or delete an entry of that name that it did not write (it records each entry's `guidId` in the connection's `native_service_id` when it writes it; a same-named entry with another GUID is the user's: "A Windows VPN named %@ already exists. Rename or delete it in Settings → Network & internet → VPN.").
- **Entry names are derived from the connection ID**: `WinVPN-<UUID upper-case>` (43 characters, below `RAS_MaxEntryName` = 256; passes `RasValidateEntryNameW`). Stable across renames (no `RasRenameEntryW`), never derived from user text, and never equal to anything in the user's phonebooks. Windows shows it as the adapter name in `ipconfig` ("PPP adapter WinVPN-…"); the user guide explains it. `macvpn_core::ras::names` builds and recognises them, and the `RasEngine` refuses to write, dial or delete any entry of its phonebook whose name is not `WinVPN-` + a UUID (`winsys` stays generic: it knows nothing of WinVPN, as its crate docs say).
- **When entries are written:** L2TP (and Cisco under option B) keep the macOS model: **Save** writes the entry (`NativeProfiles::build` + `install`; no approval step on Windows, so the button reads **Save** on Windows: a `windows` variant of "Save and Install Profile"). IKEv2 and SSTP keep the helper model: each `up` writes the entry from the config it is given (the config may have changed in the vault or through a team catalog since the last connect), then dials. Every entry is rewritten in full (`RasSetEntryPropertiesW` replaces the entry), so no stale option survives. Deleting a connection deletes its entry (new `NativeProfiles::remove`, Task 6), and a launch sweep deletes entries of the private phonebook whose UUID is no longer a connection of the open vault (Task 13; never while the vault is locked).

### Credentials

- **The password (and the OTP code appended to it) is passed at dial time only**, in `RASDIALPARAMSW.szPassword` (and `szUserName` / `szDomain`) of `RasDialW`; it is never stored by WinVPN in Windows (`RasSetEntryDialParamsW` is never called with a password; `RASEO2_CacheCredentials` is off, so Windows does not save it either). This is the counterpart of macOS' `SCNetworkConnectionStart` user options and matches spec 4.2 ("RAS dial parameters supply them at connect time, so nothing is stored in the phonebook"). `RASDIALPARAMSW` lives in a `Zeroizing` buffer and is wiped right after `RasDialW` returns. The vault stays the only place WinVPN keeps it.
- **The PSK has no dial-time field** (`RASDIALPARAMSW` has none): Windows takes it only from its RAS credential store, written with `RasSetCredentialsW(…, RASCM_PreSharedKey)` (Microsoft Learn, *RASCREDENTIALS*: "RASCM_PreSharedKey … the pre-shared key"; Windows keeps it encrypted for the user). So WinVPN writes the PSK there **at every connect, just before dialling** (from the vault: the vault stays the source of truth, a PSK changed in WinVPN or by a team catalog is used at once), keeps it while the entry exists (IKE rekeys need it), and clears it (`fClearCredentials`) before deleting the entry. This is exactly the macOS trade-off documented in `crates/core/src/mobileconfig.rs` (the PSK stays in the system's profile). The PSK is never in the phonebook file (the spike checks the file has no PSK bytes).
- **Credential Manager is not involved** (the vault key only, 2a). Windows' RAS credential store is per user and works without the WinVPN Service. **Task 2: `RasSetCredentialsW(RASCM_PreSharedKey)` works over SSH too** (no 1312), so the PSK tests run over SSH; `RasGetCredentialsW` never returns the PSK (a 16-character placeholder; "stored" = `dwMask` has `RASCM_PreSharedKey`); after `RasDeleteEntryW` and re-creating the name no PSK is found (WinVPN still clears it explicitly before every delete).
- **System VPNs** (the user's own entries) keep MacVPN's model: their PSK / password can be stored in WinVPN's vault (`save_system_secrets`, L2TP labels only, as on macOS) and are passed the same way at connect; without stored secrets WinVPN uses Windows' own saved credentials (`RasGetEntryDialParamsW`), and if Windows has none it shows Windows' own sign-in dialog (`RasDialDlgW`, the counterpart of macOS asking for a missing password).

### Per-kind mapping

The pure translation (`macvpn_core::ras`, Task 3) produces a `RasEntryPlan` (strategy, server, options, IPsec policy, metrics, DNS behaviour, credentials needed); `winsys::ras` encodes it into `RASENTRYW` (Task 5). Exact flag values are pinned against the reference entries the spike captured from `Add-VpnConnection` on the VM (Task 2, `crates/winsys/tests/fixtures/ras/`), so WinVPN's entries equal what Microsoft's own tool writes for the same choices. **Common to every entry (Task 2):** `dwType = RASET_Vpn`, `dwfNetProtocols = RASNP_Ip | RASNP_Ipv6`, `dwFramingProtocol = RASFP_Ppp`, `szDeviceType = "vpn"` with an **empty** `szDeviceName` (Windows picks the WAN Miniport; no `RasEnumDevicesW`), `dwSubEntries` 1, `dwDialMode` 0, `dwRedialCount` 3 / `dwRedialPause` 60, `RASEO2_DontNegotiateMultilink | RASEO2_ReconnectIfDropped`; never the dialler-UI bits (`RASEO_PreviewUserPw`, `PreviewDomain`, `ShowDialingProgress`, `ModemLights`) nor `RASEO2_CacheCredentials`. Full tunnel = `RASEO_RemoteDefaultGateway | RASEO2_IPv6RemoteDefaultGateway` (Microsoft's `-SplitTunneling` clears exactly these two).

The IKEv2 custom policy is written as the two phonebook keys Windows itself writes for `Set-VpnConnectionIPsecConfiguration` (`NumCustomPolicy=1`, `CustomIPSecPolicies=<hex>`): `RASENTRYW` has no field for it. **The byte layout, pinned by Task 2** (three reference policies, `ikev2_policy{,_gcm,_3des}.pbk`): 24 bytes = six little-endian DWORDs in the order **1 IntegrityCheckMethod, 2 EncryptionMethod, 3 DHGroup, 4 CipherTransformConstants, 5 AuthenticationTransformConstants, 6 PfsGroup** (not `ROUTER_CUSTOM_IKEv2_POLICY0`'s order), numbered as the VpnClient enums:

| Field | Values |
|---|---|
| IntegrityCheckMethod | MD5 0, SHA1 1, SHA256 2, SHA384 3 |
| EncryptionMethod | DES 0, DES3 1, AES128 2, AES192 3, AES256 4, GCMAES128 5, GCMAES256 6 (no GCMAES192) |
| DHGroup | None 0, Group1 1, Group2 2, Group14 3, ECP256 4, ECP384 5, Group24 6 |
| CipherTransformConstants | DES 1, DES3 2, AES128 3, AES192 4, AES256 5, GCMAES128 6, GCMAES192 7, GCMAES256 8 |
| AuthenticationTransformConstants | MD596 0, SHA196 1, SHA256128 2, GCMAES128 3, GCMAES192 4, GCMAES256 5 |
| PfsGroup | None 0, PFS1 1, PFS2 2, PFS2048 3, ECP256 4, ECP384 5, PFSMM 6, PFS24 7 |

The plan's default (`WINDOWS_DEFAULT_FOR_STRONGSWAN`) is exactly `ikev2_policy.pbk`: `020000000400000003000000050000000200000000000000` (2, 4, 3, 5, 2, 0). WinVPN writes the keys with `WritePrivateProfileStringW` into its own phonebook only, and **after every `RasSetEntryPropertiesW`** — `NumCustomPolicy=1` + the blob, or `NumCustomPolicy=0` and no `CustomIPSecPolicies` key — because a rewrite keeps whatever policy keys were there (it writes `NumCustomPolicy=0` only when it creates the section; Task 2); then it reads them back to check. The file stays ANSI.

### Split tunnel, routes and DNS

- **Full tunnel** = `RASEO_RemoteDefaultGateway` (+ `RASEO2_IPv6RemoteDefaultGateway`): MacVPN's "Send all traffic over VPN" (L2TP, SSTP `route_all`) and IKEv2 with `remote_ts = 0.0.0.0/0` or no `remote_ts`.
- **Split tunnel** for L2TP and SSTP = Windows' default behaviour without the default gateway: the class-based route plus the routes the server pushes (DHCP option 249), which is what macOS' PPP does without "Send all traffic". No per-entry route list exists in MacVPN's L2TP/SSTP settings, so none is added. IKEv2 split tunnels use the negotiated traffic selectors as routes (`RASEO2_PlumbIKEv2TSAsRoutes`), the counterpart of strongSwan installing `remote_ts`.
- **DNS** comes from the server (PPP IPCP / IKEv2 configuration payload) and is applied by Windows to the RAS adapter, as macOS applies the pushed DNS. SSTP `peer_dns = no` (MacVPN: do not use the server's DNS) has no RAS switch: WinVPN sets the entry's explicit IPv4/IPv6 interface metric high (`RASEO2_IPv4ExplicitMetric`, metric 9000) so the physical adapter's DNS is preferred; the guide calls it "best effort on Windows" and the checklist checks `nslookup`. WinVPN changes no DNS setting of any adapter itself (no service involvement).

### Status, the live list and the log

- **Status** comes from `RasEnumConnectionsW` (each `RASCONNW` carries the entry name *and* the phonebook path — Task 2: `szPhonebook` is the path **exactly as the dialler passed it**, letter case included, no `\\?\` — : a connection is WinVPN's only when the path equals this user's private phonebook path compared without regard to letter case, and the name is `WinVPN-<UUID>`; anything else is a system VPN or another user's; WinVPN itself always passes the one path it builds), `RasGetConnectStatusW` (connecting / connected / error code) and `RasGetProjectionInfoEx` for the tunnel's IPv4 address (the card's IP, as macOS shows it).
- **Watching:** a `winsys::ras::Watcher` thread waits on (a) an auto-reset event registered with `RasConnectionNotificationW(INVALID_HANDLE_VALUE, event, RASCN_Connection | RASCN_Disconnection)` (any RAS connection appears or ends), (b) `FindFirstChangeNotificationW` on the two default phonebook folders and on WinVPN's `ras` folder (an entry added, changed or removed in Settings), and (c) its stop event; each wake calls `on_change` (the manager's debounced reload), exactly like macOS' `SCPreferences` watcher. A default phonebook folder that does not exist yet is watched through its nearest existing parent (filtered to the `Pbk` name); a phonebook *file* comes and goes (Windows deletes it with its last entry: "no file" = "no entries"). **Task 2: the RAS connection notification is only a hint** — at the desktop it fired after the L2TP failure only, never for SSTP/IKEv2 failures or hang-ups, and never over SSH — so a RASCN event means "reload now", and the manager's poll (`RasEnumConnectionsW` / `RasGetConnectStatusW`) is the source of truth for system VPNs; WinVPN's own dials are followed through their dial callback.
- **The log:** the RAS kinds have no engine log on Windows, so the `RasEngine` writes its own masked log per connection (`%LOCALAPPDATA%\WinVPN\logs\ras\<UUID>.log`, private ACL, the 2b size caps): each dial state (`RASCS_*` names, e.g. "Connecting to vpn.example.com…", "Authenticating…", "Connected, IPv4 10.8.0.6"), the entry's effective settings in debug mode (never a secret), the IPsec policy chosen for IKEv2, and every error as "Windows error <code>: <RasGetErrorStringW text>" plus WinVPN's explanation (Task 7). The Log tab reads it through the existing `LogSource` (2b). This is a Windows improvement over macOS' native kinds (which have no log); it is not a parity gap.

### System VPNs (the user's own Windows VPNs)

- `NativeController::list` returns the managed entries (private phonebook) and the entries of the two default phonebooks (`RasEnumEntriesW(NULL, NULL, …)` enumerates the all-users and the current user's phonebooks; `RASENTRYNAMEW.szPhonebookPath` tells which), each with its status. A default-phonebook entry becomes a `SystemVpn { id: its guidId (UUID string, so secret_id() works), name: its entry name, type_label: L2TP | IKEv2 | SSTP | VPN, status }`. `type_label` gets one new value, **`SSTP`** (Windows only; the UI shows labels as given; `supports_stored_secrets()` stays L2TP/Cisco).
- Managed entries are listed with `id = "WinVPN-<UUID>"` and bind to their connection through a new `NativeController::managed_service_id(&Uuid) -> Option<String>` (default `None`: macOS binds by name and server as before; Windows returns the entry name), checked first in `manager::match_service`. So the existing "managed services are not system VPNs" filter works unchanged.
- Start/stop of a system VPN: `RasDialW` on its own phonebook path with the vault's stored secrets (L2TP), else the entry's saved credentials (`RasGetEntryDialParamsW`), else Windows' dialog (`RasDialDlgW` on a worker thread: the user signs in in Windows' own window); stop = `RasHangUpW`. WinVPN never edits, renames or deletes a system VPN entry.

### Import, export, backup, catalogs

- The formats do not change (spec 5): a connection is the same vault record on both OSes; MacVPN's `.sstp` / strongSwan / L2TP / Cisco connections restore and import on Windows as they are. There is no Windows-only export format and no `.pbk` import (MacVPN has no `.mobileconfig` import either).
- **Restore / import / catalog apply** call `NativeProfiles::install` for L2TP connections (as on macOS, where it stages profiles): on Windows that writes the entries silently (no approval step), so a restored MacVPN backup's L2TP connections are ready at once. IKEv2/SSTP entries are written at the first connect. Connections Windows cannot run (Cisco under A; IKEv2/SSTP settings Windows lacks) are kept and marked with their reason (the row's `unavailable_reason`, the editor's yellow note), as spec 5 says; they stay fully usable on macOS through the same backup or catalog.

### Logoff, quit, uninstall

- **Logoff** (2b decision 2): Windows itself hangs up the RAS connections a user dialled when the user logs off, unless an administrator set `KeepRasConnections` = 1 (`HKLM\SOFTWARE\Microsoft\Windows NT\CurrentVersion\Winlogon`). WinVPN adds two safety nets: the app hangs up its own connections in `WM_ENDSESSION` (logoff only, not shutdown handling changes), and the WinVPN Service, on `WTS_SESSION_LOGOFF` of a SID with no session left, hangs up every RAS connection whose phonebook is that user's `…\AppData\Local\WinVPN\ras\WinVPN.pbk` (Task 10: no request, no user input; the profile path comes from `HKLM\…\ProfileList\<SID>\ProfileImagePath`). Locking and user switching keep them (as 2b).
- **Quit:** the existing "There are active VPN connections" question covers RAS connections (disconnect or keep running). A RAS connection outlives the app process (RasMan owns it); at the next launch the `RasEngine` finds it by entry name and shows it connected (the counterpart of the root layer's connections surviving a MacVPN quit).
- **Uninstall** (MSI): the per-user private phonebook stays in `%LOCALAPPDATA%\WinVPN` with the rest of the user's data (2a decision: data stays); it is inert without WinVPN (it is not a default phonebook, so Windows lists nothing from it). A connection still up during uninstall stays up until the user signs out (or runs `rasdial /disconnect`); the guide says "Disconnect before uninstalling". The PSKs Windows stored for WinVPN's entries: Task 2 checks whether `RasDeleteEntryW` also clears an entry's stored PSK; WinVPN clears it explicitly before every delete anyway, and the guide states the checked behaviour for entries left behind by an uninstall (and how to remove them: open WinVPN before uninstalling and delete the connections, or keep the folder for a reinstall).

### Administrator steps (never through the service)

- **Trusting a CA for SSTP / IKEv2** (Windows checks server certificates against the *computer's* Trusted Root store for these VPNs): **Trust This CA in Windows…** in the SSTP (cert = ca) and IKEv2 editors. WinVPN writes the PEM's DER to a fresh file in its private temp folder, holds it open with `FILE_SHARE_READ` only (no swap while elevated), and runs `%SystemRoot%\System32\certutil.exe -addstore Root "<file>"` with `runas` (one UAC confirmation by an administrator), then checks the store (`CertOpenStore` read-only, by SHA-1 thumbprint) and reports. Before that it shows the CA's subject, validity and SHA-256 fingerprint and the warning "Every program on this PC will trust certificates from this CA." This must never be a service operation: a standard user could otherwise make the whole machine trust any CA.
- **L2TP/IPsec behind NAT**: Windows refuses L2TP to a server behind NAT unless `HKLM\SYSTEM\CurrentControlSet\Services\PolicyAgent\AssumeUDPEncapsulationContextOnSendRule` = 2 (Microsoft Learn, *Configure an L2TP/IPsec server behind a NAT-T device*; error 809). When an L2TP dial ends with 809, the error text offers **Allow L2TP Behind NAT…**: `%SystemRoot%\System32\reg.exe add HKLM\SYSTEM\CurrentControlSet\Services\PolicyAgent /v AssumeUDPEncapsulationContextOnSendRule /t REG_DWORD /d 2 /f` with `runas`, then "Restart Windows to apply it."
- **Computer certificates for IKEv2** are imported by an administrator with Windows' own tool (`certlm.msc`); WinVPN gives the steps and never handles the `.p12` password (a `certutil -importpfx -p` would put it in argv).

### Errors

`RasDialW` and the connection state return Windows error codes. Task 7 maps the common ones to WinVPN texts that say what to do (EN + HU), and appends Windows' own text (`RasGetErrorStringW`, in Windows' display language) to the log only: 691 / 13801 (authentication / IKE credentials), 789 / 13806 (IPsec negotiation / no computer certificate), 809 (blocked or behind NAT), 812 (policy), 13868 (no matching IKE proposal: names the policy WinVPN offered), 0x800B0109 / 0x80092013 / 0x800B010F (SSTP certificate untrusted / revocation unknown / name mismatch), 868 (server name not resolved), 800 / 815 (no answer), 720 / 734 (PPP), 619 / 628 / 631 (closed by the server / the user). Anything else: "Windows error %@ (see the log)". **Task 2 adds** (what a dial to a silent host really returns, and the hang-up codes): 789 for L2TP (no answer / IPsec failed: 65 s), `0x8007274C` for SSTP (`WSAETIMEDOUT` as HRESULT: the server did not answer; 21 s), 628 for IKEv2 (no answer or closed: 5 s), 618 / 31 / 87 after WinVPN's own hang-up (cancelled, not an error: any code after our hang-up), 633 (the VPN device is still busy: retry after a moment), 756 (already dialling), 766 for an L2TP PSK entry without a stored PSK, `0x80004005` (unspecified). HRESULT codes arrive as negative `i32`: compare as `u32`. Task 7 is merged; these are its addendum G-12 (Task 15).

### Cisco IPsec on Windows (research for open question 1)

- Windows' IKE/AuthIP service (`IKEEXT`) speaks IKEv1 only for L2TP/IPsec and transport-mode policies; it has no XAUTH or Mode Config client, so no RAS strategy can carry a Cisco-style remote-access IPsec connection.
- **strongSwan for Windows** (`charon-svc` with `kernel-wfp`): the strongSwan documentation (*docs.strongswan.org → Windows*) says no binaries are provided (MinGW builds only), "not all functionality is ported", the IP Helper backend "does not support the installation of virtual IP addresses" (a remote-access client needs the virtual IP that Mode Config assigns), and the socket plugin requires Windows' `IKEEXT` service to be stopped or disabled — which would break every native L2TP/IKEv2 connection on the PC. Not viable.
- **Shrew Soft VPN Client 2.2.2**: the last release is from 2013; integrators (Intra2net, Kerio, WatchGuard) no longer recommend it; it has an unpatched local privilege escalation (CVE-2019-25283, unquoted service path) and a filter driver reported to break networking on Windows 11. No update stream exists, so requirement 3 cannot be met. Not acceptable.
- **vpnc / libreswan / racoon** have no Windows ports; **NCP Secure Entry** and **TheGreenBow** are commercial, per-seat licensed and not redistributable; **Cisco Secure Client** speaks IKEv2/SSL only.
- **Conclusion:** there is no maintained, redistributable, signed engine. Option A (implemented by default, Task 12) or option B (a WinVPN-built IKEv1 engine, separate spec and plan) are the honest choices; question 1.
