# LinVPN phase L-b (VPNs through NetworkManager): implementation plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking. The spec is `docs/superpowers/specs/2026-10-29-linvpn-design.md` (decisions 1–8 and their dated notes, sections 3–8; L-b is section 5 item 3). The spike findings are binding facts: `docs/superpowers/spikes/2026-10-29-linvpn-nm-openvpn.md` (L0-1), `…-redirect-gateway.md` (L0-1b), `…-wireguard-liveness.md` (L0-3), `…-tray.md` (L0-2), `…-baseline.md`. Every rule, decision and "Resolved point" of the L0+L-a plan (`docs/superpowers/plans/2026-10-29-linvpn-l0-la.md`) still applies unless this plan says why it deviates. The WinVPN 2b and 2c plans (`2026-10-22-winvpn-2b-service-openvpn-wireguard.md`, `2026-10-25-winvpn-2c-native-vpns.md`) are the model for how engines, `HelperClient`, `NativeController`, `NativeProfiles`, `NativeSupport`, liveness, traffic, logs and missing engines are wired; `crates/platform-win/src/win/ras_engine.rs` is the reference implementation of an in-process engine. Where this plan and the spec disagree, the spec wins, except where "Resolved points" below says why the plan deviates.

**Goal:** LinVPN connects every kind MacVPN has (WireGuard, OpenVPN, L2TP/IPsec, IKEv2, Cisco IPsec, SSTP) through NetworkManager as the non-admin desktop user, with MFA (appended code, static challenge, CRV1) through LinVPN's own NM secret agent, a server-pushed `redirect-gateway` honoured through LinVPN's own patched NM OpenVPN service, the user's own NM VPNs as system VPNs, live status, traffic and dead-tunnel detection, auto-reconnect on network loss/switch and wake, the Log tab fed by the read-only `linvpn-logd`, missing NM plugins installed through PackageKit with the system's own prompt, and NM/systemd-resolved DNS with split DNS. MacVPN and WinVPN behave exactly as in 2.0.5.

**Architecture:** a pure translation `macvpn_core::nm_plan` turns a LinVPN connection into NM settings (a neutral value tree, no secret, tested on every OS). `crates/platform-linux/src/lin/nm/` holds the system side: the NM D-Bus client (`AddAndActivateConnection2`, `persist = volatile` (no `bind-activation` since resolved point 19), `permissions = user:<name>` before adding, a non-interactive polkit pre-check before every write), the secret agent (answers only NetworkManager's unique bus name, only for connections LinVPN activated), the engine that implements `HelperClient` (OpenVPN, WireGuard, IKEv2, SSTP) and `NativeController`/`NativeProfiles`/`NativeSupport` (L2TP, Cisco, system VPNs) exactly as WinVPN splits them, sysfs counters, the NM network watcher, plugin detection and PackageKit. `linvpn-logd` is a third binary of the helper crate, socket-activated by systemd, not root (a dynamic user in `systemd-journal`). The patched NM OpenVPN service is upstream `NetworkManager-openvpn` 1.12.5 plus LinVPN's patch, built in CI from a SHA-256-pinned tarball and shipped in the `.deb` under its own name next to the untouched stock plugin.

**Tech Stack:** Rust 1.99.1 (edition 2024), `zbus =5.19.0` (blocking API, as L-a pinned it), `libc 0.2.191`, `serde_json` (already in core), NetworkManager 1.54.3 / network-manager-openvpn 1.12.5 / OpenVPN 2.7.0 (Ubuntu 26.04, the VM), PackageKit's system D-Bus API, polkit `CheckAuthorization`, systemd socket activation, `journalctl -o json`, C (the plugin patch; GPL-2+), meson or autotools (upstream's own build), bash, Svelte + TS.

3. **The trait split this plan follows (WinVPN 2c, `platform-win/src/win/platform.rs`):** `HelperClient` runs the "helper kinds" (here OpenVPN, WireGuard, IKEv2 = `VPNKind::Strongswan`, SSTP); `NativeController` + `NativeProfiles` run the native kinds (L2TP, Cisco) and the system VPNs; `managed_service_id(&uuid)` names the platform's own service of a managed native connection, so it is never shown as a system VPN; `NativeSupport::unsupported_reason(connection, config)` is asked for **every** kind at every reload (`app-core/src/manager.rs::read_config_facts`) and greys a row with the reason; `NativeSupport::editor_notes` fills the editor's platform notes.
4. **Secrets reach the platform already prepared by app-core:** `Secrets { username, password, psk, key_password, one_time_code, challenge_packed }`; with a static challenge `password` is already `SCRV1:…` or `password+code` (`challenge_packed = true`); with "append a one-time code" the code is already appended. The dynamic challenge (CRV1) goes through `AuthStateReader` (the platform reports a challenge) and `HelperClient::respond(id, AuthResponseKind::Crv1, code)`.
5. **NM facts measured on the VM (spikes L0-1, L0-3):** `AddAndActivateConnection2(settings, "/", "/", {"persist": "volatile", "bind-activation": "dbus-client"})` (measured with the binding; LinVPN drops it since resolved point 19, which changes neither the polkit actions nor the volatile deletion) with `connection.permissions = ["user:<name>"]` needs no prompt in the desktop session or the user manager (`settings.modify.own`, `network-control`: yes) and NM deletes the profile on deactivation; without `permissions` it is `settings.modify.system` = admin password **on the desktop**. From a plain SSH shell every NM write is `auth` (challenge). `nmcli connection import` is never used. `wg`/netlink cannot read WireGuard peers without root; `/sys/class/net/<if>/statistics/{rx,tx}_bytes` is readable. NM-openvpn 1.12.5 refuses any `vpn.data` key outside its `valid_properties[]`; it starts OpenVPN with `--verb 1`, `--route-noexec`, `--ifconfig-noexec`, `--management … --management-query-passwords --auth-retry interact`, `--syslog nm-openvpn`, `--user nm-openvpn --group nm-openvpn --chroot /var/lib/openvpn/chroot`. It handles CRV1 (secret `challenge-response`, hints `x-dynamic-challenge[-echo]:challenge-response`) but has no static-challenge key (the agent answers `password` in the packed form). OpenVPN 2.7 exports `route_redirect_gateway_ipv4/6` to `--up`; the stock helper ignores them.
6. **The VPN lab** (`scripts/vpn-lab/`): `profiles.sh` writes `client/macos`, `client/windows`, `client/selftest`; the lab serves every kind (README table), routes only `10.99.0.0/24`, and has no IPv6. The lab runs in Docker on the Mac; the VM is a separate machine on the LAN. **Whether the VM reaches the Mac's published ports is not confirmed yet** (CP-lab's first step checks it).

## Rules carried into every task (R1–R12)

Every task prompt the coordinator writes **includes this block verbatim**; each task below says "Rules R1–R12".

- **R1 No polkit or admin dialogs on the live desktop.** No agent action may make the VM's desktop show an authentication dialog. NM writes happen only (a) in tests against a fake NM on a private bus (`dbus-run-session`), or (b) through `scripts/lin-remote.sh desktop` (the user manager, which polkit counts as the session) **after** a non-interactive `CheckAuthorization` (flags 0) says `authorized=true, challenge=false` for `org.freedesktop.NetworkManager.settings.modify.own` and `org.freedesktop.NetworkManager.network-control`, and only for connections with `connection.permissions = ["user:<name>"]` set before adding. Never `nmcli connection import`, never `nmcli connection add` without `connection.permissions`, never a D-Bus call with the `ALLOW_INTERACTIVE_AUTHORIZATION` flag, never `pkexec`, never PackageKit's `InstallPackages` against the real system bus. A step that would need any of these is a **maintainer checkpoint** with its exact text.
- **R2 No sudo, no installs by agents.** Agents never run `sudo`, `apt`, `apt-get`, `dpkg -i`, `snap`, `pip install --user` on the VM or the Mac's system. Packages, `.deb` installs and build dependencies are the maintainer's, at a checkpoint.
- **R3 One VM dir per agent.** Each concurrent agent uses its own `LINVPN_REMOTE_DIR=linvpn-work-slot<N>` (N = 1 … 3, reused warm, never deleted after a task). The lab E2E tasks (Wave B4) run alone on the VM (one agent, `slot1`), because NM's state and the desktop are global.
- **R4 Memory on the VM (7 GB RAM):** every remote cargo command runs with `CARGO_BUILD_JOBS=2`, and at most **two** agents build on the VM at the same time (the coordinator serializes a third). Example: `scripts/lin-remote.sh run 'CARGO_BUILD_JOBS=2 cargo test --locked -p macvpn-platform-linux --test nm_client'`. The plugin build (Task 4) uses `-j2` / `ninja -j 2`.
- **R5 No VM, LAN or lab addresses and no company name in the repository.** Never commit an IP of the VM, the Mac or the lab's LAN binding, nor the maintainer's company name in any spelling (the lab's internal `10.99.0.0/16` addresses are already public in `scripts/vpn-lab/README.md` and may be used). Examples use `vpn.example.com`, `192.0.2.0/24`, `198.51.100.0/24`, `lab.example.test`. Lab state stays in the git-ignored `scripts/vpn-lab/.state/`; files copied to the VM go through `scripts/lin-remote.sh put` into `.linvpn-put/` (git-ignored there).
- **R6 TDD:** the failing test first; pure logic tested on the Mac (`cargo test -p <crate> --test <name>`), Linux code on the VM through `scripts/lin-remote.sh run 'CARGO_BUILD_JOBS=2 dbus-run-session -- cargo test --locked -p <crate> --test <name>'`. Targeted tests per task; the coordinator runs the full gate once per wave (L-a's "Rules for every task", gate list unchanged, plus `scripts/lin-remote.sh test`).
- **R7 File ownership:** a task edits only the files its "Files" list names. The shared files (`crates/platform-linux/src/lin/platform.rs`, `crates/platform-linux/src/lib.rs`, `crates/platform-linux/src/lin/mod.rs`, `crates/platform-linux/src/lin/nm/mod.rs`, `crates/platform-linux/src/pure/mod.rs`, `crates/core/src/lib.rs`, `crates/core/src/nm_plan/mod.rs`, `crates/core/l10n/strings.json`, every `Cargo.toml`, `scripts/ignored-everywhere.txt`) are edited only by Task 1 (the skeleton) and the wave's wiring task. A task that needs a new user-facing string writes it into **its own fragment** `crates/core/l10n/lb/<task number>.json` (same entry schema as `strings.json`); the wiring task merges the fragments (`node scripts/l10n-merge.mjs`).
- **R8 Secrets:** never in a log, argv, env, a window title, a notification, a D-Bus property, `NmPlan::settings`, a `Debug` output or a test failure message: passwords, PSKs, key passwords, OTP codes, WireGuard private and preshared keys, key file contents. ## Resolved points (where the spec leaves a choice open, and where this plan deviates)

1. **Which trait runs which kind (WinVPN 2c's split).** `HelperClient` runs OpenVPN, WireGuard, IKEv2 (`VPNKind::Strongswan`) and SSTP: each `up` builds the plan from the config it is given (a team catalog or an edit may have changed it), writes the runtime files, adds and activates the connection. `NativeController`/`NativeProfiles` run L2TP and Cisco IPsec (their settings live in `Connection::native`, not in a config) and the system VPNs. One `lin::nm::Engine` implements all of them, so status, the agent and the logs are one state.
2. **Managed L2TP/Cisco "profiles":** `NativeProfiles::install` writes **no NM connection** (they are volatile per connect, spec section 4). It stores a secret-free *plan record* (`$XDG_DATA_HOME/LinVPN/nm/<UUID>.json`, dir 0700, file 0600: kind, server, account, group, send-all-traffic) so `NativeController::list` can list `linvpn-<UUID>` (status from NM) and `start` can build the connection. `needs_approval() = false`, `removes_profiles() = true` (`remove` deletes the record), `PlatformNotes::no_install_step = true` (the button reads **Save**, as on Windows). `managed_service_id(id) = Some("linvpn-<UUID>")`.
3. **The NM connection's UUID is derived, not random:** `nm_uuid = UUIDv8(SHA-256("linvpn-nm-v1\0" ‖ uid as u32 LE ‖ connection UUID bytes)[..16])`. Reasons: (a) a stale volatile connection of a crashed run is found and deleted before the next add; (b) `linvpn-logd` proves ownership **without state and after the volatile connection is gone**: it recomputes the UUID from the caller's `SO_PEERCRED` uid and the LinVPN connection id the caller names, so a caller can only ever ask for UUIDs derived from its own uid (a preimage of SHA-256 would be needed to reach another user's). This replaces the spec's "the connection's `permissions` holds `user:<caller>`", which logd cannot check once NM has deleted the connection; the `permissions` rule still holds for every connection LinVPN adds.
4. **"Send all traffic over VPN" for OpenVPN is stored in the config itself**, not in a new `Connection` field (R10): **Always** = a `redirect-gateway def1` line (plus `ipv6` when the profile had it), **Never** = `pull-filter ignore "redirect-gateway"`, **Server decides** = neither (and no `route-nopull`). `macvpn_core::openvpn_routing` reads and rewrites these lines; the editor's three-way control (Linux only, `only: ["linux"]` texts) edits the config text. So the choice syncs through backups, exports and team catalogs, means the same on macOS (whose OpenVPN honours these directives itself), and needs no format change. A profile that already says it keeps meaning it (L0-1's rule).
5. **Linux refusals are platform reasons, not FORBIDDEN.** The 8 "Not supported on Linux" entries of L0-1 (`peer-fingerprint`, `verify-hash`, `remote-cert-ku`, `remote-cert-eku`, `route … net_gateway|remote_host`, an unflattenable `<connection>`, a `pull-filter` pattern the service cannot pass, `compress stub|stub-v2|migrate`) come from `nm_plan::openvpn` as `Unsupported` reasons → `NativeSupport::unsupported_reason` greys the row with the reason, the editor shows it, the start is refused, and the config stays valid for macOS and Windows (spec 3.2). 6. **LinVPN's NM OpenVPN service patch has two parts** (L0-1b's "required" and "optional but small" parts, both taken): the helper sends `NEVER_DEFAULT` from `route_redirect_gateway_ipv4/6` (OpenVPN ≥ 2.7); the service accepts four extra `vpn.data` keys passed to OpenVPN — `linvpn-redirect-gateway` (flags), `linvpn-pull-filter` (newline-separated `ignore|accept|reject "<prefix>"` lines), `linvpn-route-nopull` (`yes`), `linvpn-verb` (`0`–`4`) — and starts OpenVPN with `--syslog linvpn-ovpn-<NM connection UUID>` so logd can attribute OpenVPN's lines. Every argument is validated in C against the same character rules as the Rust side. With the service part, `pull-filter`/`route-nopull` are passed to OpenVPN itself and the L0-1 "emulate with `ignore-auto-*`" path is only the fallback for OpenVPN < 2.7 (where `nm_plan` still sets `never-default` itself, decision 7).
7. **OpenVPN < 2.7** (not the target; Debian 13): `nm_plan` gets `Caps::openvpn_push_visible = false` (the engine reads `openvpn --version` as the user); "Server decides" then acts as decision 7 (profile's `redirect-gateway` → full, else split: `ipv4/ipv6.never-default = yes`), and System Status' OpenVPN row says why.
8. **Secret delivery:** by default every secret is `AGENT_OWNED` (flags 1) and LinVPN's agent answers (spec). Spike L0-4 decides the agent order versus GNOME Shell's agent: **branch A** (NM asks LinVPN's agent first, or GNOME Shell's agent declines the service types it has no auth dialog for) keeps agent-owned secrets everywhere; **branch B** (GNOME Shell's agent prompts) switches the static secrets (password, PSK, key password, WireGuard keys) to `Caps::secret_mode = Inline`: flags 0 and the values put into the volatile in-memory connection right before `AddAndActivateConnection2` (never stored on disk by NM: the connection is unsaved and volatile; readable over D-Bus only by root and the `permissions` user), while CRV1 stays agent-only and System Status says "the dynamic challenge needs …" if GNOME still grabs it. Task 14 implements both; Task 2's result sets the default constant `pure::nm::agent::DEFAULT_SECRET_MODE`.
9. **`linvpn-logd` is not root:** a socket-activated `Accept=yes` service with `DynamicUser=yes`, `SupplementaryGroups=systemd-journal`, sandboxed (`ProtectSystem=strict`, `PrivateNetwork=yes`, `RestrictAddressFamilies=AF_UNIX`, `NoNewPrivileges=yes`, `CapabilityBoundingSet=`). The spec's "the only root component" becomes "no root component" for logs. It lives in the helper crate as a third `[[bin]]` (`crates/helper/src/linux/logd*.rs`, the cfg rule's allowed place); its pure protocol and filter are `macvpn_core::logd` (tested on every OS). It runs `/usr/bin/journalctl` with fixed arguments (only validated UUIDs, numbers and a validated cursor are interpolated, each as its own argv element) and filters the JSON in Rust.
10. **Which journal lines are the caller's:** NM's own lines with the journal field `NM_CONNECTION=<nm_uuid>` (fallback, if Task 18 Step 1 finds NM 1.54.3 does not write that field: a `MESSAGE` that starts with `vpn[0x…,<nm_uuid>,` or contains `(<nm_uuid>)`); OpenVPN's lines with `SYSLOG_IDENTIFIER=linvpn-ovpn-<nm_uuid>` (resolved point 6); the other plugins' lines (`charon-nm`, `nm-l2tp-service`, `xl2tpd`, `pppd`, `nm-sstp-service`, `sstpc`, `nm-vpnc-service`, `vpnc`, `nm-openvpn`, `nm-openvpn-serv`) **only inside the connection's own window** (first to last NM line of `nm_uuid`) **and only if no other VPN connection** (an NM line with `NM_LOG_DOMAINS` containing `VPN` and another `NM_CONNECTION`) appears in that window; otherwise those plugin lines are withheld and one line says so. 19. **Tunnels outlive LinVPN's process (2026-10-30, a parity fix after Task 29; it supersedes "bound to this D-Bus client" in fact 5, Task 13 and Task 21):** `AddAndActivateConnection2` gets only `{"persist": "volatile"}`. With `bind-activation = dbus-client` NM took every LinVPN tunnel down when the process ended, also after **Quit, Keep Them Running**, unlike macOS and Windows. Now: a normal quit disconnects through app-core's quit flow (`down` → `Engine::deactivate`); a "Keep Them Running" quit or a crash leaves the tunnel up (the security trade-off macOS and Windows already make: the user disconnects from LinVPN's next launch or GNOME's network menu, and the volatile profile still vanishes on deactivation). //! The names LinVPN gives NetworkManager: the derived connection UUID (resolved point 3: also linvpn-logd's
//! ownership proof) and the tunnel interface names. A contract between the app and `linvpn-logd`: never change the
//! derivation without a new domain string.

use sha2::{Digest, Sha256};
use uuid::Uuid;

const DOMAIN: &[u8] = b"linvpn-nm-v1\0";
pub const IFACE_WIREGUARD: &str = "lvw";
pub const IFACE_OPENVPN: &str = "lvo";
/// The `NativeController` service id of a managed L2TP / Cisco connection.
pub const SERVICE_PREFIX: &str = "linvpn-";

/// `UUIDv8(SHA-256(DOMAIN ‖ uid LE ‖ id))`: version 8, RFC 4122 variant.
pub fn nm_uuid(uid: u32, id: &Uuid) -> Uuid {
    let mut h = Sha256::new();
    h.update(DOMAIN);
    h.update(uid.to_le_bytes());
    h.update(id.as_bytes());
    let digest = h.finalize();
    let mut b = [0u8; 16];
    b.copy_from_slice(&digest[..16]);
    b[6] = (b[6] & 0x0F) | 0x80;
    b[8] = (b[8] & 0x3F) | 0x80;
    Uuid::from_bytes(b)
}

/// The same derivation written out byte by byte, as `linvpn-logd`'s documentation states it (the pinned test
/// compares both, so a refactor of [`nm_uuid`] cannot silently change it).
pub fn nm_uuid_reference(uid: u32, id: &Uuid) -> String {
    let mut input = DOMAIN.to_vec();
    input.extend_from_slice(&uid.to_le_bytes());
    input.extend_from_slice(id.as_bytes());
    let d = Sha256::digest(&input);
    let mut b: Vec<u8> = d[..16].to_vec();
    b[6] = (b[6] & 0x0F) | 0x80;
    b[8] = (b[8] & 0x3F) | 0x80;
    Uuid::from_slice(&b).expect("16 bytes").hyphenated().to_string()
}

/// `<prefix><8 lower-case hex digits of SHA-256(id)>` (11 characters; IFNAMSIZ is 16 with the NUL).
pub fn iface(prefix: &str, id: &Uuid) -> String {
    let d = Sha256::digest(id.as_bytes());
    format!("{prefix}{:02x}{:02x}{:02x}{:02x}", d[0], d[1], d[2], d[3])
}

/// `linvpn-<UUID upper-case>` (the managed L2TP / Cisco service id; resolved point 2).
pub fn service_id(id: &Uuid) -> String {
    format!("{SERVICE_PREFIX}{}", id.hyphenated().to_string().to_uppercase())
}

/// The id of [`service_id`], or `None`.
pub fn parse_service_id(s: &str) -> Option<Uuid> {
    crate::models::parse_uuid(s.strip_prefix(SERVICE_PREFIX)?)
}

//! DNS through NetworkManager and systemd-resolved (spec 4 "DNS"): LinVPN has no DNS manager. A split tunnel uses
//! the connection's DNS only for its domains (routing-only `~domain` entries); a full tunnel takes every query
//! (`~.`) with a negative priority (resolved then asks only this link). Pushed DNS (OpenVPN's `dhcp-option`, PPP,
//! IKEv2 configuration payload) is applied by NM itself; these extras only add what the plan knows.

use super::NmValue;
use std::collections::BTreeMap;

/// NM's default priority for VPNs is 50; a split tunnel keeps it.

/// Negative: only this connection's DNS is used while it is up.
pub const FULL_PRIORITY: i32 = -50;

/// The `ipv4` / `ipv6` DNS keys for a tunnel. `full`: the plan knows it is a full tunnel; `domains`: the search
/// domains the config names (without a leading `~`).
pub fn section_extras(full: bool, domains: &[String]) -> BTreeMap<String, NmValue> {
    let mut s = BTreeMap::new();
    let mut search: Vec<String> = if full {
        domains.iter().map(|d| d.trim_start_matches('~').to_string()).collect()
    } else {
        domains.iter().map(|d| format!("~{}", d.trim_start_matches('~'))).collect()
    };
    if full {
        search.push("~.".into());
    }
    if !search.is_empty() {
        s.insert("dns-search".into(), NmValue::StrList(search));
    }
    s.insert("dns-priority".into(), NmValue::I32(if full { FULL_PRIORITY } else { SPLIT_PRIORITY }));
    s
}

`scripts/l10n-merge.mjs`:

```js
#!/usr/bin/env node
// Merges the L-b string fragments (crates/core/l10n/lb/<task>.json) into crates/core/l10n/strings.json: entries
// appended in numeric fragment order, an identical existing entry accepted, a different one refused (nothing is
// written then). The fragments are deleted after a successful write. Usage: node scripts/l10n-merge.mjs
import { readFileSync, writeFileSync, readdirSync, unlinkSync } from 'node:fs';
import { join, dirname } from 'node:path';
import { fileURLToPath } from 'node:url';
import { isDeepStrictEqual } from 'node:util';

export function merge(tablePath, fragmentDir) {
  const table = JSON.parse(readFileSync(tablePath, 'utf8'));
  const files = readdirSync(fragmentDir).filter((f) => /^\d+\.json$/.test(f)).sort((a, b) => parseInt(a) - parseInt(b));
  for (const f of files) {
    const { strings } = JSON.parse(readFileSync(join(fragmentDir, f), 'utf8'));
    for (const [key, entry] of Object.entries(strings)) {
      const old = table.strings[key];
      if (old !== undefined && !isDeepStrictEqual(old, entry)) throw new Error(`${f}: "${key}" already exists with another entry`);
      table.strings[key] = entry;
    }
  }
  writeFileSync(tablePath, JSON.stringify(table, null, 2) + '\n');
  for (const f of files) unlinkSync(join(fragmentDir, f));
  return files.length;
}

if (process.argv[1] === fileURLToPath(import.meta.url)) {
  const root = join(dirname(fileURLToPath(import.meta.url)), '..');
  const n = merge(join(root, 'crates/core/l10n/strings.json'), join(root, 'crates/core/l10n/lb'));
  console.log(`merged ${n} fragment(s)`);
}
```
